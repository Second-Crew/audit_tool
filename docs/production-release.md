## Shared dashboard controls

`supabase/dashboard-admission.sql` creates separate request-attempt and lease tables. A PostgreSQL advisory transaction lock makes the five-attempts-per-ten-minutes address limit and two-active-audits limit atomic across instances. Busy attempts count toward the address limit. Preview, Production and local scopes are separate; all branch Previews sharing one database share Preview capacity. This control is independent of the agent API.

The API stores an HMAC of the forwarded address using the server-only Supabase key, never the raw address or key. On Vercel, [the platform overwrites X-Forwarded-For](https://vercel.com/docs/headers/request-headers). Any other host must overwrite forwarding headers at a trusted reverse proxy; do not expose this handler directly with client-controlled headers. Key rotation changes address hashes, temporarily resetting the address quota, while the global ceiling remains intact.

Successful and failed audits release their lease after persistence. A disconnected client does not release capacity while the audit continues. A terminated instance leaves its lease until the 15-minute expiry. This conservatively outlasts the route's 300-second Vercel function lifetime. Do not use this fixed lease on a host that permits audits longer than 15 minutes without adding renewal or a hard execution bound. Denied requests include Retry-After. Database failures fail closed; no per-instance fallback is used once shared controls are enabled. Production analyze also fails closed when `DASHBOARD_SHARED_LIMITS_ENABLED` is not `true`.

Review/apply the migration in a dedicated Preview database, then enable the flag for Preview only and redeploy. Verify two-instance admission/release, rate rejection, database-outage rejection, client disconnect, and terminated-instance recovery through the hosted RPC before approving Production activation. Leases and attempts are cleaned when another reservation arrives in their scope; stale metadata can remain in an idle scope, so it is not a strict scheduled retention guarantee.

## Access and storage

The dashboard uses one shared internal-team password. It does not provide separate users, tenant isolation, per-user revocation, or an access audit trail. Release scope must remain one trusted team. Password rotation invalidates current cookies. The HTTP-only, Secure, SameSite=Lax cookie gates workspace APIs and exports; `/r/<send-id>` deliberately serves only prospect HTML without the team cookie. Treat that UUID link as a bearer link, not a confidential workspace link.

Apply the separately reviewable `supabase/workspace-access.sql` only after inspecting existing policies. It explicitly denies public, anon and authenticated roles direct table access and grants server service-role CRUD; the same restrictions are in new-install `schema.sql`. [Supabase RLS and database function guidance](https://supabase.com/docs/guides/database/postgres/row-level-security), [function guidance](https://supabase.com/docs/guides/database/functions) support RLS, explicit function grants, and a fixed empty search path on security-definer functions.

Run `supabase/workspace-storage-checks.sql` read-only in each intended hosted database and save restricted evidence of its results. Require RLS on clients/audits/report_sends, no direct anon/authenticated grants, no permissive unexpected policies, and server CRUD. Admission tables have no direct browser grants; only the server can call their RPCs. The existing `record_report_open(uuid)` function must also be inspected for safe search_path and service-only execution. `workspace-storage-checks.sql` includes its signature and definition for restricted administrator review. The separately reviewable `report-tracking.sql` supplies the repository’s now-defined version: UUID `send_id`, UUID audit-id result, atomic increment, fixed empty search path and invoker rights. It depends on the server’s table grants and bypass-RLS role rather than granting extra definer privileges. The hosted signature/body/grants were inspected and its argument name/result type are compatible; applying the replacement remains held until Preview isolation and migration approval. Unexpected definitions in another target need a separately reviewed compatibility change. Do not drop an existing function or execute it on a real send merely to test access. Tracked hosting still requires hosted verification and an internal disposable smoke fixture before inclusion in release scope.

Reports, Markdown, HTML, workspace summaries and raw observation panels are JSON/text in the `audits` table. There is no Supabase Storage bucket in this implementation. Raw panels are separately saved in `report.observed_panel`; the workspace summary and prospect exports use aggregates, not the raw panel or conversation permalinks. Current Preview and Production Supabase URL values were confirmed identical on 2026-10-03; no branch override exists. Configure a dedicated Preview database through an explicitly approved configuration change before any hosted migration/activation or destructive failure fixture. The sensitive key was withheld from environment pulls, and existing deployed values were not exposed by the READY-deployment pull path, so do not equate current project settings with a comparison of deployed secrets. No secret values or report rows are needed in the release evidence.

Saving a client followed by an audit is two requests, not a transaction. If audit insertion fails, client metadata may have been updated while no report was saved. The response must remain `failed`, with usable local exports, and history must not claim success. Simulate this against an isolated Preview fixture; also verify database unavailability on history, reopen, and exports returns bounded safe errors. Supabase requests have a 15-second timeout. Do not send or log private row details/credentials as error text.

## Retention decision required

No automatic saved-report/raw-panel retention is implemented. Do not silently turn on deletion. A concrete proposal for owner review is **90 days for saved reports and associated send/contact records, 30 days for raw observation panels**, with raw-panel removal preserving dated aggregate counts and exports. This is a proposal, not an agreed policy or legal requirement. Also decide whether older reports may remain prospect-accessible, whether explicit re-audit replaces or preserves history, and how deletion/export requests are handled.

After approval, implement a bounded, server-only cleanup job with dry-run counts, restricted execution, idempotence and error alerts. Test that panel cleanup preserves report aggregates and excludes private permalinks from exports; report deletion should invalidate associated tracked links via the existing cascade. Inventory backups, provider logs, downloaded exports and already-shared links separately; deleting a database row does not recall a downloaded report or immediately remove backups. Verify retention in Preview before a Production change is approved. The user prohibited recurring chat automations; no automation has been created here.
