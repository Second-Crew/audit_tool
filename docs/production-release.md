## Shared dashboard controls

`supabase/dashboard-admission.sql` creates separate request-attempt and lease tables. A PostgreSQL advisory transaction lock makes the five-attempts-per-ten-minutes address limit and two-active-audits limit atomic across instances. Busy attempts count toward the address limit. Preview, Production and local scopes are separate; all branch Previews sharing one database share Preview capacity. This control is independent of the agent API.

The API stores an HMAC of the forwarded address using the server-only Supabase key, never the raw address or key. On Vercel, [the platform overwrites X-Forwarded-For](https://vercel.com/docs/headers/request-headers). Any other host must overwrite forwarding headers at a trusted reverse proxy; do not expose this handler directly with client-controlled headers. Key rotation changes address hashes, temporarily resetting the address quota, while the global ceiling remains intact.

Successful and failed audits release their lease after persistence. A disconnected client does not release capacity while the audit continues. A terminated instance leaves its lease until the 15-minute expiry. This conservatively outlasts the route's 300-second Vercel function lifetime. Do not use this fixed lease on a host that permits audits longer than 15 minutes without adding renewal or a hard execution bound. Denied requests include Retry-After. Database failures fail closed; no per-instance fallback is used once shared controls are enabled. Hosted Preview and Production analyze fail closed when `DASHBOARD_SHARED_LIMITS_ENABLED` is not `true`.

The migration and flag are active only in the isolated branch Preview. Hosted RPC concurrency/rate/release, actual busy/expiry admission, unavailable-RPC rejection and client disconnect passed. Verify distinct-instance routing and real terminated-instance recovery before approving Production activation; fixture expiry alone does not prove process termination. Leases and attempts are cleaned when another reservation arrives in their scope; stale metadata can remain in an idle scope, so it is not a strict scheduled retention guarantee.

## Access and storage

The dashboard uses one shared internal-team password. It does not provide separate users, tenant isolation, per-user revocation, or an access audit trail. Release scope must remain one trusted team. Password rotation invalidates current cookies. The HTTP-only, Secure, SameSite=Lax cookie gates workspace APIs and exports; `/r/<send-id>` deliberately serves only prospect HTML without the team cookie. Treat that UUID link as a bearer link, not a confidential workspace link.

Apply the separately reviewable `supabase/workspace-access.sql` only after inspecting existing policies. It explicitly denies public, anon and authenticated roles direct table access and grants server service-role CRUD; the same restrictions are in new-install `schema.sql`. [Supabase RLS and database function guidance](https://supabase.com/docs/guides/database/postgres/row-level-security), [function guidance](https://supabase.com/docs/guides/database/functions) support RLS, explicit function grants, and a fixed empty search path on security-definer functions.

Run `supabase/workspace-storage-checks.sql` read-only in each intended hosted database and save restricted evidence of its results. Require RLS on clients/audits/report_sends, no direct anon/authenticated grants, no permissive unexpected policies, and server CRUD. Admission tables have no direct browser grants; only the server can call their RPCs. The existing `record_report_open(uuid)` function must also be inspected for safe search_path and service-only execution. `workspace-storage-checks.sql` includes its signature and definition for restricted administrator review. The separately reviewable `report-tracking.sql` supplies the repository’s now-defined version: UUID `send_id`, UUID audit-id result, atomic increment, fixed empty search path and invoker rights. It depends on the server’s table grants and bypass-RLS role rather than granting extra definer privileges. The original hosted signature/body/grants were compatible. The replacement is applied and verified in isolated Preview; applying it to Production remains held. Unexpected definitions in another target need a separately reviewed compatibility change. Do not drop an existing function or execute it on a real send merely to test access. Hosted RPC counting passed on an internal disposable fixture; public tracked HTML/access still needs a smoke check before inclusion in release scope.

Reports, Markdown, HTML, workspace summaries and raw observation panels are JSON/text in the `audits` table. There is no Supabase Storage bucket in this implementation. Raw panels are separately saved in `report.observed_panel`; the workspace summary and prospect exports use aggregates, not the raw panel or conversation permalinks. Preview and Production URL values were identical on October 3. On October 5, this branch received isolated Preview overrides and the owner-created empty project received the reviewed migrations. Other Preview branches can still inherit the original shared values; do not run these fixtures there. Production remains on the original database. The sensitive key was withheld from environment pulls, and existing deployed values were not exposed by the READY-deployment pull path, so do not equate current project settings with a comparison of deployed secrets. No secret values or report rows are needed in the release evidence.

Saving a client followed by an audit is two requests, not a transaction. If audit insertion fails, client metadata may have been updated while no report was saved. The response must remain `failed`, with usable local exports, and history must not claim success. The isolated insertion-failure fixture and safe history read failure passed. Hosted reopen/export outage checks remain incomplete after the Chrome block; do not infer their result from local tests. Supabase requests have a 15-second timeout. Do not send or log private row details/credentials as error text.
